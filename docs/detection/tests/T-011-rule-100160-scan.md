# T-011 - Règles 100160 / 100161 : scan d'endpoints

- **Date :** 20-10-2026
- **Auteur :** Meghan CRESCI-HUMANN
- **Version Wazuh :** 4.14.9 (single-node)
- **Contrat :** CONTRACT.md v0.3.0-draft (§8)
- **Règles testées :** 100160, 100161
- **Fichier de règles :** `detection/rules/100160_scan.xml`
- **MITRE ATT&CK :** T1595.003 - Active Scanning: Wordlist Scanning
- **Statut :** ✅ Validé

## Contexte

Un outil de découverte de contenu (ffuf, gobuster, dirb) teste des centaines de chemins pour trouver des pages cachées. La grande majorité renvoie des réponses 4xx (surtout 404). Une rafale de 4xx depuis une même IP est donc un bon indicateur de scan.

## Règles testées

```xml
<rule id="100160" level="4">
  <if_sid>100100</if_sid>
  <field name="http.response.status_code" type="pcre2">^4\d\d$</field>
  <description>SupportDesk: client error $(http.response.status_code) on $(http.request.path) from $(source.ip)</description>
  <group>web,client_error,</group>
</rule>

<rule id="100161" level="10" frequency="15" timeframe="30">
  <if_matched_sid>100160</if_matched_sid>
  <same_field>source.ip</same_field>
  <description>SupportDesk: possible endpoint scanning from $(source.ip) (many 4xx responses)</description>
  <mitre><id>T1595.003</id></mitre>
  <group>web_attack,scan,</group>
</rule>
```

### Choix de conception

- **100160 - erreur client isolée (niveau 4)** : toute réponse 4xx. Niveau bas : une 404 isolée est banale (lien mort, favicon absent).
- **100161 - scan (niveau 10)** : au moins 15 réponses 4xx depuis la même IP (`same_field source.ip`) en 30 secondes.
- **Seuil volontairement élevé** (15 / 30 s) pour ne pas alerter sur un utilisateur qui croise quelques 404 en navigant. À confirmer avec le script de trafic normal.

## Cas testés

### Règle unitaire (`wazuh-logtest`)

Une réponse 404 sur `/admin.php` → `100160`, niveau 4 ✅
Description : `SupportDesk: client error 404 on /admin.php from 203.0.113.42`.

### Corrélation (chaîne complète)

15 réponses 404 sur des chemins différents (`/path1.php` … `/path15.php`), espacées d'1 s, depuis la même IP :

```bash
for i in $(seq 1 15); do
  sed "s|/admin.php|/path$i.php|" detection/samples/scan_404.jsonl >> detection/logs/app.jsonl
  sleep 1
done
```

| Mesure                            | Avant | Après | Attendu | Résultat |
| --------------------------------- | ----- | ----- | ------- | -------- |
| Alertes 100161 dans `alerts.json` | 0     | 1     | +1      | ✅       |

Indexation : aucune erreur ; l'alerte indexée porte la description `SupportDesk: possible endpoint scanning from 203.0.113.42 (many 4xx responses)`.

### Observation : corrélation en rafale espacée

Contrairement au brute force de T-005 (5 événements simultanés → 0 alerte), cette rafale de 15 événements espacés d'1 s se déclenche correctement. Cela confirme la conclusion de T-005 : la corrélation échoue surtout quand les événements arrivent **dans la même lecture du fichier**, pas quand ils sont simplement nombreux. Un intervalle d'1 s suffit à les séparer.

## Limites connues

- **Scan lent** : moins de 15 requêtes en 30 s (ralentissement volontaire) passe sous le seuil. Piste d'évasion bonus.
- **Rotation d'IP** : `X-Forwarded-For` falsifiable (contrat §4.2) répartit les 4xx sur plusieurs IP et casse la corrélation.
- **Rafale simultanée** : comme pour le brute force, un envoi très rapide pourrait sous-compter (à mesurer pendant l'attaque réelle).
- **Chevauchement** : 100160 matche aussi les 404 d'un path traversal (T-007), qui déclenche en parallèle 100140. Comportement acceptable (deux angles de détection), à garder en tête pour le rapport de qualification.

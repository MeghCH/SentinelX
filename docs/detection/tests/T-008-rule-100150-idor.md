# T-008 - Règles 100150 / 100151 : IDOR sur l'export de tickets

- **Date :** 20-10-2026
- **Auteur :** Meghan CRESCI-HUMANN
- **Version Wazuh :** 4.14.9 (single-node)
- **Contrat :** CONTRACT.md v0.3.0-draft (§4.3, §8, D-011, D-013)
- **Règles testées :** 100150, 100151
- **Fichier de règles :** `detection/rules/100150_idor.xml`
- **Statut :** ✅ Validé (5 cas sur 5) - indexation de `target.owner_id` et `target.owned_by_user` confirmée

## Contexte

`GET /tickets/:id/export` renvoie un ticket complet (avec ses commentaires) **sans vérifier que l'utilisateur connecté en est le propriétaire**. Il suffit de changer l'identifiant dans l'URL pour exporter le ticket de quelqu'un d'autre : c'est une IDOR (Insecure Direct Object Reference).

Cette attaque ne produit aucune erreur : la réponse est un 200 normal. Elle n'est détectable que par une **règle métier** comparant le demandeur et le propriétaire. Les règles Wazuh ne pouvant pas comparer deux champs d'un même événement, l'application fournit le résultat de la comparaison dans `target.owned_by_user` (contrat D-013).

## Règles testées

```xml
<rule id="100150" level="8">
  <if_sid>100100</if_sid>
  <field name="event.action">^export$</field>
  <field name="target.type">^ticket$</field>
  <field name="target.owned_by_user">^false$</field>
  <field name="user.role" negate="yes">^admin$</field>
  <description>SupportDesk: user $(user.name) exported ticket $(target.id) owned by another user ($(target.owner_id))</description>
  <group>web_attack,idor,</group>
</rule>

<rule id="100151" level="10" frequency="5" timeframe="300">
  <if_matched_sid>100150</if_matched_sid>
  <same_field>user.id</same_field>
  <different_field>target.id</different_field>
  <description>SupportDesk: possible ticket enumeration (IDOR) by user $(user.name) from $(source.ip)</description>
  <group>web_attack,idor,</group>
</rule>
```

### Choix de conception

- **100150 - accès isolé (niveau 8)** : un export du ticket d'autrui est anormal, mais peut avoir une explication (ticket partagé, erreur de lien). Niveau moyen.
- **Exclusion des administrateurs** (`negate="yes"` sur `user.role`) : exporter n'importe quel ticket fait partie du rôle d'admin. Sans cette exclusion, chaque export légitime d'un admin serait un faux positif.
- **100151 - énumération (niveau 10)** : un même utilisateur (`same_field user.id`) qui exporte au moins 5 tickets **différents** (`different_field target.id`) d'autres personnes en 5 minutes. Ce comportement correspond à un parcours systématique des identifiants, signe d'une exploitation volontaire.
- **Corrélation par utilisateur et non par IP** : l'IDOR exige d'être connecté, et l'identité de session est plus fiable que `source.ip`, falsifiable via `X-Forwarded-For` (contrat §4.2).

### Énumération (chaîne complète)

**Cas positif** - jdoe exporte 5 tickets différents (11 à 15), espacés de 3 s :

```bash
for id in 11 12 13 14 15; do
  sed "s|/tickets/7/export|/tickets/$id/export|; s|\"id\":\"7\",\"owner_id\"|\"id\":\"$id\",\"owner_id\"|" \
    detection/samples/ticket_export.jsonl >> detection/logs/app.jsonl
  sleep 3
done
```

**Cas négatif** - msmith (id 4) exporte 5 fois **le même** ticket :

```bash
for i in 1 2 3 4 5; do
  sed 's|"user":{"id":"3","name":"jdoe"|"user":{"id":"4","name":"msmith"|' \
    detection/samples/ticket_export.jsonl >> detection/logs/app.jsonl
  sleep 3
done
```

Mesure : nombre d'alertes 100151 dans `alerts.json` avant et après chaque cas.

| Cas                   | Avant | Après | Attendu | Résultat |
| --------------------- | ----- | ----- | ------- | -------- |
| 5 tickets différents  | 0     | 1     | +1      | ✅       |
| 5 fois le même ticket | 1     | 1     | +0      | ✅       |

### Indexation

```bash
docker logs --since 5m sentinelx-wazuh.manager-1 2>&1 | grep -iE "cannot index|mapper_parsing"
curl -sk -u admin:SecretPassword \
  "https://localhost:9200/wazuh-alerts-*/_search?q=rule.id:100150&size=1" \
  | python3 -m json.tool | grep -E '"owner_id"|"owned_by_user"'
```

Résultat : aucune erreur d'indexation ; l'alerte indexée contient `"owner_id": "5"` et `"owned_by_user": "false"`.

**Les champs `target.owner_id` et `target.owned_by_user` sont validés de bout en bout** : avec T-006 et T-007, tous les nouveaux champs du contrat v0.3.0 sont désormais validés.

## Limites connues

- **Dépendance à l'application** : la détection repose entièrement sur `target.owned_by_user`, calculé par l'application. Si le logger ne le remplit pas ou le calcule mal, aucune alerte. À vérifier lors du dry-run avec l'application V1.
- **Énumération lente** : moins de 5 tickets différents en 5 minutes passe sous le seuil de 100151 (chaque export reste néanmoins signalé par 100150).
- **Rafales** : comme pour le brute force (T-005), la corrélation peut sous-compter des exports très rapprochés. À mesurer pendant l'attaque réelle.
- **Autres routes** : `GET /tickets/:id` présente la même absence de contrôle, mais seule l'action `export` est couverte par cette règle.
- **Pas de mapping MITRE** : aucune technique ATT&CK ne décrit précisément l'IDOR ; la règle n'en déclare pas, conformément au contrat §8.

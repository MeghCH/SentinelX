# T-011 - Rules 100160 / 100161: endpoint scanning

- **Date:** 20-10-2026
- **Author:** Meghan CRESCI-HUMANN
- **Wazuh version:** 4.14.9 (single-node)
- **Contract:** CONTRACT.md v0.3.0-draft (§8)
- **Rules tested:** 100160, 100161
- **Rule file:** `detection/rules/100160_scan.xml`
- **MITRE ATT&CK:** T1595.003 - Active Scanning: Wordlist Scanning
- **Status:** ✅ Validated

## Context

A content discovery tool (ffuf, gobuster, dirb) tests hundreds of paths to find hidden pages. The vast majority return 4xx responses (mostly 404). A burst of 4xx from the same IP is therefore a good indicator of scanning.

## Rules tested

```xml
<rule id="100160" level="4">
  <if_sid>100100</if_sid>
  <field name="http.response.status_code" type="pcre2">^4\d\d$</field>
  <description>SupportDesk: client error $(http.response.status_code) on $(http.request.path) from $(source.ip)</description>
  <group>web,client_error,</group>
</rule>

<rule id="100161" level="10" frequency="15" timeframe="30">
  <if_matched_sid>100160</if_matched_sid>
  <same_field>source.ip</same_field>
  <description>SupportDesk: possible endpoint scanning from $(source.ip) (many 4xx responses)</description>
  <mitre><id>T1595.003</id></mitre>
  <group>web_attack,scan,</group>
</rule>
```

### Design choices

- **100160 - one-off client error (level 4)**: any 4xx response. Low level: an isolated 404 is commonplace (dead link, missing favicon).
- **100161 - scanning (level 10)**: at least 15 4xx responses from the same IP (`same_field source.ip`) within 30 seconds.
- **Deliberately high threshold** (15 / 30 s) so as not to alert on a user hitting a few 404s while browsing. To be confirmed with the traffic script.

## Cases tested

### Single rule (`wazuh-logtest`)

A 404 response on `/admin.php` → `100160`, level 4 ✅
Description: `SupportDesk: client error 404 on /admin.php from 203.0.113.42`.

### Correlation (full chain)

15 404 responses on different paths (`/path1.php` … `/path15.php`), 1 s apart, from the same IP:

```bash
for i in $(seq 1 15); do
  sed "s|/admin.php|/path$i.php|" detection/samples/scan_404.jsonl >> detection/logs/app.jsonl
  sleep 1
done
```

| Measurement                       | Before | After | Expected | Result |
| --------------------------------- | ------ | ----- | -------- | ------ |
| 100161 alerts in `alerts.json`    | 0      | 1     | +1       | ✅     |

Indexing: no errors; the indexed alert carries the description `SupportDesk: possible endpoint scanning from 203.0.113.42 (many 4xx responses)`.

### Observation: correlation with spaced bursts

Unlike the T-005 brute force (5 simultaneous events → 0 alerts), this burst of 15 events spaced 1 s apart triggers correctly. This confirms the T-005 conclusion: correlation fails mainly when the events arrive **in the same read of the file**, not simply when they are numerous. A 1 s interval is enough to separate them.

## Known limitations

- **Slow scan**: fewer than 15 requests in 30 s (deliberate slowdown) falls under the threshold. Bonus evasion lead.
- **IP rotation**: a spoofed `X-Forwarded-For` (contract §4.2) spreads the 4xx across several IPs and breaks the correlation.
- **Simultaneous burst**: as with brute force, a very fast send could be undercounted (to be measured during the real attack).
- **Overlap**: 100160 also matches the 404s of a path traversal (T-007), which simultaneously triggers 100140. Acceptable behavior (two detection angles), to keep in mind for the qualification report.

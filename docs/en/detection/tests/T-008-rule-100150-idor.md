# T-008 - Rules 100150 / 100151: IDOR on ticket export

- **Date:** 20-10-2026
- **Author:** Meghan CRESCI-HUMANN
- **Wazuh version:** 4.14.9 (single-node)
- **Contract:** CONTRACT.md v0.3.0-draft (§4.3, §8, D-011, D-013)
- **Rules tested:** 100150, 100151
- **Rule file:** `detection/rules/100150_idor.xml`
- **Status:** ✅ Validated (5 out of 5 cases) - indexing of `target.owner_id` and `target.owned_by_user` confirmed

## Context

`GET /tickets/:id/export` returns a full ticket (with its comments) **without checking that the logged-in user owns it**. Changing the identifier in the URL is enough to export someone else's ticket: this is an IDOR (Insecure Direct Object Reference).

This attack produces no error: the response is a normal 200. It can only be detected by a **business rule** comparing the requester and the owner. Since Wazuh rules cannot compare two fields of the same event, the application provides the comparison result in `target.owned_by_user` (contract D-013).

## Rules tested

```xml
<rule id="100150" level="8">
  <if_sid>100100</if_sid>
  <field name="event.action">^export$</field>
  <field name="target.type">^ticket$</field>
  <field name="target.owned_by_user">^false$</field>
  <field name="user.role" negate="yes">^admin$</field>
  <description>SupportDesk: user $(user.name) exported ticket $(target.id) owned by another user ($(target.owner_id))</description>
  <group>web_attack,idor,</group>
</rule>

<rule id="100151" level="10" frequency="5" timeframe="300">
  <if_matched_sid>100150</if_matched_sid>
  <same_field>user.id</same_field>
  <different_field>target.id</different_field>
  <description>SupportDesk: possible ticket enumeration (IDOR) by user $(user.name) from $(source.ip)</description>
  <group>web_attack,idor,</group>
</rule>
```

### Design choices

- **100150 - one-off access (level 8)**: exporting someone else's ticket is abnormal, but may have an explanation (shared ticket, link error). Medium level.
- **Exclusion of administrators** (`negate="yes"` on `user.role`): exporting any ticket is part of the admin role. Without this exclusion, every legitimate admin export would be a false positive.
- **100151 - enumeration (level 10)**: the same user (`same_field user.id`) exporting at least 5 **different** tickets (`different_field target.id`) belonging to others within 5 minutes. This behavior matches a systematic walk through the identifiers, a sign of deliberate exploitation.
- **Correlation by user and not by IP**: IDOR requires being logged in, and the session identity is more reliable than `source.ip`, which can be spoofed via `X-Forwarded-For` (contract §4.2).

## Procedure and results

### Single cases (`wazuh-logtest`)

| Case                           | Sample                      | Expected         | Obtained                  |
| ------------------------------ | --------------------------- | ---------------- | ------------------------- |
| Export of someone else's ticket | `ticket_export.jsonl`      | 100150, level 8  | ✅ 100150, level 8        |
| Export of one's own ticket     | `ticket_export_own.jsonl`   | no alert         | ✅ 100100 only, level 0   |
| Export by an administrator     | `ticket_export_admin.jsonl` | no alert         | ✅ 100100 only, level 0   |

Obtained description: `SupportDesk: user jdoe exported ticket 7 owned by another user (5)`.

### Enumeration (full chain)

**Positive case** - jdoe exports 5 different tickets (11 to 15), 3 s apart:

```bash
for id in 11 12 13 14 15; do
  sed "s|/tickets/7/export|/tickets/$id/export|; s|\"id\":\"7\",\"owner_id\"|\"id\":\"$id\",\"owner_id\"|" \
    detection/samples/ticket_export.jsonl >> detection/logs/app.jsonl
  sleep 3
done
```

**Negative case** - msmith (id 4) exports **the same** ticket 5 times:

```bash
for i in 1 2 3 4 5; do
  sed 's|"user":{"id":"3","name":"jdoe"|"user":{"id":"4","name":"msmith"|' \
    detection/samples/ticket_export.jsonl >> detection/logs/app.jsonl
  sleep 3
done
```

Measurement: number of 100151 alerts in `alerts.json` before and after each case.

| Case                    | Before | After | Expected | Result |
| ----------------------- | ------ | ----- | -------- | ------ |
| 5 different tickets     | 0      | 1     | +1       | ✅     |
| 5 times the same ticket | 1      | 1     | +0       | ✅     |

### Indexing

```bash
docker logs --since 5m sentinelx-wazuh.manager-1 2>&1 | grep -iE "cannot index|mapper_parsing"
curl -sk -u admin:SecretPassword \
  "https://localhost:9200/wazuh-alerts-*/_search?q=rule.id:100150&size=1" \
  | python3 -m json.tool | grep -E '"owner_id"|"owned_by_user"'
```

Result: no indexing errors; the indexed alert contains `"owner_id": "5"` and `"owned_by_user": "false"`.

**The `target.owner_id` and `target.owned_by_user` fields are validated end to end**: with T-006 and T-007, all the new fields of contract v0.3.0 are now validated.

## Known limitations

- **Dependence on the application**: detection relies entirely on `target.owned_by_user`, computed by the application. If the logger does not fill it in or computes it wrongly, no alert. To be checked during the dry-run with application V1.
- **Slow enumeration**: fewer than 5 different tickets in 5 minutes falls under the 100151 threshold (each export is nevertheless flagged by 100150).
- **Bursts**: as with brute force (T-005), correlation may undercount very tightly spaced exports. To be measured during the real attack.
- **Other routes**: `GET /tickets/:id` has the same missing check, but only the `export` action is covered by this rule.
- **No MITRE mapping**: no ATT&CK technique precisely describes IDOR; the rule declares none, per contract §8.
